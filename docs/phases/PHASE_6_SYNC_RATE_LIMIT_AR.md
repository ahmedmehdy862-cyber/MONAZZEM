# المرحلة 6 (شريحة ٥) — تقييد معدل `/api/sync` (Phase 6)

> الفرع: `phase6-web-sync-foundation` (كوميت خامس داخل المرحلة 6).
> الحالة: **مُنفَّذة محليًا، غير منشورة**. لا بناء APK ولا نشر ولا رفع إصدار.

## نطاق هذه الشريحة

إغلاق الخطر المؤجَّل منذ شريحة ١: منع تخمين كلمة مرور المزامنة وتعداد معرّفات الحسابات عبر طلبات متكررة. لا تغيير في خوارزمية الحماية ولا في القائمة البيضاء للبيانات؛ الخدمة نفسها والبيانات المخزّنة في Blob كما هما.

## ما تغيّر

### 1. مُقيَّد جديد (`lib/sync-rate-limit.js` — جديد)

- نافذة ثابتة ١٥ دقيقة: ١٠ محاولات لتفعيل الحساب، و٣٠ لكل من `pull` و`push`.
- `register` يُقَيَّد حسب عنوان المصدر، حتى لا يتمكن مصدر واحد من تجربة معرّفات كثيرة؛ `pull`/`push` يُقَيَّدان حسب `profileId`، فيبقى عزل الحسابات قائمًا ولا يتأثر مستخدم بفشل آخر.
- النجاح يُصفّر العدّاد، والفشل يزيده، والطلب المرفوض لا يستهلك خانة إضافية. أخطاء التخزين لا تُحتسب كفشل للمستخدم لأنها لا تُسجَّل في العدّاد.
- الدوال `evaluate`/`after` نقية وقابلة للاختبار، و`createLimiter()` يسمح باختبار معزول لكل حالة.

### 2. نقطة النهاية (`api/sync.js`)

- فحص القيود قبل التنفيذ، واستجابة `429` مع `Retry-After` و`Cache-Control: no-store` عند التجاوز.
- دوال `register`/`pull`/`push` تُعيد `{status, body}` بدل كتابة الاستجابة، فيُسجَّل النجاح أو الفشل في مكان واحد دون تكرار المنطق.
- الأفعال غير المعروفة تُرفض `400` قبل احتساب أي محاولة.
- لا يُسجَّل في السجلات أي `profileId` أو كلمة مرور أو عنوان مصدر؛ رسالة الخطأ العامة كما كانت.

### 3. الاختبارات (`scripts/test-sync.cjs`)

- انتهاء النافذة وإعادة الضبط عند النجاح، والحد الأقصى للفشل.
- خنق `pull` بعد ٣٠ فشلًا مع بقاء حساب آخر قابلًا للمحاولة، ورفض فعل غير معروف `400`.
- خنق `register` من نفس العنوان حتى مع تغيير `profileId`، وعدم تأثر عنوان آخر.
- عزل حالة المُقيَّد بين الاختبارات عبر `createLimiter()`، فلا تعتمد النتائج على ترتيب التنفيذ.

## التحقق

- `npm run test:sync`: **١٣/١٣** ناجحة.
- `npm run test:web` ٦/٦ و`npm run test:targeting` ٢٢/٢٢: لا انحدار.
- `npm run check` و`npm run build` و`node --check` للملفات الثلاثة: ناجحة.
- `git diff --check`: لا أخطاء محتوى (تحذيرات EOL فقط مطابقة لإعداد المستودع).
- لم يُعاد تشغيل Gradle: لا تغيير في كود Android هذه الشريحة؛ آخر نتيجة ١٩٤/١٩٤ و`lintDebug` بلا أخطاء.

## الخصوصية والتوافق

- لا Supabase ولا خدمة خارجية جديدة؛ العدّاد في ذاكرة نسخة الدالة فقط، ولا يُكتب في Blob.
- لم تتغيّر القائمة البيضاء، ولا قواعد الدمج، ولا استجابة أي إجراء ناجح.
- لم يتغيّر `DB_VERSION=14` أو الإصدار `0.29.0 / 37` أو أي مسار قديم.

## حد معروف

العدّاد داخل نسخة الدالة اللاحقة ويعاد ضبطه عند `cold start`، ومع عدة نسخ متزامنة قد يتجاوز العدد الحدّ قليلًا. هذه طبقة ردع، بينما الضمان الحقيقي هو تجزئة scrypt والمقارنة الثابتة والعزل بين الحسابات. لو احتاج النشر قيمة موزّعة صارمة، فيلزم تخزين العدّاد في Blob أو مزوّد مؤقت؛ لم يُنفَّذ هنا لأنه يضيف كتبة لكل طلب ويخرج عن نطاق الشريحة.
