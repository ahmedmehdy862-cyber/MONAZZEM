# المرحلة 3 — الإشعارات (Phase 3)

> الفرع: `phase3-notifications` (من `phase2-admin-messaging`).
> الحالة: **مُنفَّذة محليًا، غير منشورة**. لا تغييرات في `update-site` ولا في متجر QUBIX.

## الهدف

جعل وصول التنبيهات المحلية متوقعًا وقابلًا للتشخيص: صلاحيات واضحة، إعادة جدولة بعد المنح أو إعادة التشغيل، تأجيلات محفوظة، وسجل تشخيصي محلي — بدون اختراع نظام دفع أو Push Token.

## ما تغيّر

### 1. صلاحية المنبّهات الدقيقة

- زر جديد في شاشة «الإشعارات» يفتح شاشة النظام `ACTION_REQUEST_SCHEDULE_EXACT_ALARM` عند الحاجة، مع بديل إلى إعدادات التطبيق.
- عند الرجوع من الشاشة، إذا تغيّرت حالة الإشعار أو المنبّهات الدقيقة تُعاد جدولة كل التنبيهات المحلية تلقائيًا.
- عند منح `POST_NOTIFICATIONS` من أي شاشة، تُعاد الجدولة فورًا؛ عند الرفض يُكتب سبب تشخيصي فقط.
- كل مسارات الجدولة (المهام، الأذكار، الصلاة، نهاية الجلسة) تمر عبر مسار واحد يسجّل رفض المنبّه الدقيق أو فشله، ويترك دائمًا منبّهًا بديلًا غير دقيق.

### 2. إصلاح عدّ التجاهل الخاطئ

- الصفوف ذات الإجراء الفارغ كانت تُعدّ «تجاهلًا»؛ بعد ثلاثة إشعارات عادية كان التطبيق يُسكت التنبيهات غير الحرجة.
- الآن يُعدّ التجاهل عند فعل صريح فقط: زر «تمّ» أو «أجّل» يسجّل إجراءه، وسحب الإشعار يُرسل `delete intent` يسجّل `ignored`.
- المنطق القابل للاختبار في `NotificationPolicy.ignoredStreakFrom(...)` يضمن أن الفراغ لا يُعدّ تجاهلًا.

### 3. تأجيلات محفوظة وإعادة محاولة

- التأجيل الناتج عن جلسة تركيز، أو ساعات الهدوء، أو نافذة صلاة، أو الحد الأدنى بين الإشعارات، لم يعد كائنًا مؤقتًا (`StoredReminder(-1, …)`) يضيع عند إعادة التشغيل.
- يُخزَّن التأجيل في جدول `reminders` الحالي بنوع مرمّز `deferred|<reason>|<kind>`، ويأخذ رقم طلب AlarmManager خاصًا به من معرّف الصف.
- `replaceReminders` تحتفظ بالتأجيلات عند إعادة حساب جدول المهمة، و`clearDeferrals` تمنع بقاء تأجيل قديم لنفس النوع.
- لو وصل تنبيه والإذن ممنوع، لا يُستهلك التنبيه؛ يُسجَّل سبب ويُجدوَل retry محلي بعد ٣٠ دقيقة. فشل التسليم يُعاد جدولته بالطريقة نفسها.
- لا تغيير في `DB_VERSION` ولا في أسماء الجداول أو الأعمدة؛ التأجيلات تستخدم الجدول الموجود.

### 4. السجل التشخيصي وإعادة التشغيل

- أُضيف `NotificationMaintenance`: مسار واحد لفحص الصلاحيات، وفتح إعدادات النظام، وإعادة جدولة كل التنبيهات، وكتابة سبب مختصر في `notification_log`.
- الأسباب الجديدة (`exact_alarm_denied`, `exact_alarm_failed`, `notification_permission_denied`, `deferred:*`, `reschedule_failed:*`) تُكتَب مرة واحدة في الساعة لكل سبب حتى لا يمتلئ الجدول.
- بطاقة «سجل تشخيصي محلي» في شاشة الإشعارات تعرض آخر ٦ أسباب خلال ٧ أيام. لا تحتوي على محتوى ملاحظات ولا مهام ولا معرّفات شخصية.
- بثّ الإقلاع، وتغيير الوقت/المنطقة الزمنية، ووظيفة إعادة الجدولة المحفوظة تستدعي الآن نفس المسار، فلا يبقى تطبيق بلا منبّهات لأن خطوة واحدة فشلت.

## حدود Push

MONAZZEM لا يملك نظام Push. لم يُنشأ FCM، ولم يُطلب Push Token، ولم تُرسل رموز إلى أي خادم. رسائل الفريق تصل لدى فتح التطبيق عبر خادم التحديثات الحالي، وهذه المرحلة تخص الإشعارات المحلية فقط.

## الملفات المعدّلة

| الملف | الغرض |
|---|---|
| `NotificationMaintenance.kt` (جديد) | صلاحية المنبّهات الدقيقة، إعادة الجدولة، والتشخيص المقيّد |
| `ReminderEngine.kt` | تأجيلات محفوظة، retry عند رفض الإذن، سحب صريح، منع استهلاك تنبيه قبل التحقق |
| `StudyDb.kt` | حفظ التأجيلات، فرز التجاهل الصريح، استعلام التشخيص |
| `NotificationPolicy.kt` | دالة نقية لعدّ التجاهل |
| `AppNotifications.kt` | دعم `delete intent` |
| `NotificationCenterScreen.kt` | حالة المنبّهات الدقيقة، إعادة الجدولة عند المنح، بطاقة التشخيص |
| `MainActivity.kt`, `SettingsSupportScreens.kt` | ردّ طلب الإذن يعيد الجدولة أو يسجّل الرفض |
| `DailyReminderReceiver.kt`, `ReminderRescheduleJob.kt`, `DhikrReminders.kt`, `PrayerTimes.kt`, `SessionAlarm.kt` | توحيد مسار الجدولة وإعادة التشغيل |
| `NotificationPolicyTest.kt`, `ReminderPersistenceTest.kt` (جديد) | ٥ اختبارات إضافية |

## التوافق والتراجع

- لا رفع للإصدار، ولا نشر، ولا دفع Git. لا تغيير في `update-site` أو متجر QUBIX.
- البيانات الحالية تبقى: الجداول والأعمدة وأسماء الملفات كما هي، والتأجيلات تُضاف إلى جدول موجود.
- التراجع: `git revert` لكوميت المرحلة؛ لا يوجد تغيير مخطط قاعدة بيانات يحتاج ترحيلًا عكسيًا.
- لم تُغيَّر المنطقة الزمنية أو اختيار IANA؛ ذلك متروك للمرحلة ٤.

## ما لم يتحقق

- لا جهاز ADB، لذلك لم تُختبر شاشة نظام المنبّهات الدقيقة ولا ظهور الإشعار فعليًا بعد المنح أو إعادة التشغيل.
- سلوك الشركات (MIUI/HyperOS وغيرها) في تأخير المنبّهات الدقيقة يبقى `Not Verified`.
- النتائج المتاحة ثابتة/مخبرية فقط: `testDebugUnitTest` و`lintDebug` و`git diff --check`.
